> 版本：v4.5 | 日期：2026-06-21
> <!-- REVIEW:v4.5 本次修订修复第四轮评审发现的 3 个 P0 问题 + 2 个补充建议 -->
> 技术栈：React Native 0.76 + Expo SDK 52 + TypeScript
> 定位：便利店商品管理工具——**不做收银/支付/结算，购物车仅用于合计看总价**
> 核心：商品 CRUD → AI/语音/扫码查价 → 模拟结账看总价（按钮显示「结账」，仅模拟合计，不做真实支付）

> - 场景：单店单人（店主自己用），单设备运行，不做多设备协同
> - 商品量：常态 < 1000 件，极限 1 万件以内
> - 核心诉求：快速查价、看总价，不是做账/盘点/进销存
> - 交互节奏：扫一下、看一下、关掉——轻、快、不强留痕迹
> 
> 评审时请勿基于「连锁门店」「多人协作」「库存管理」「收银对账」等超出上述范围的场景提出建议。

## 一、设计理念

### 三大原则（评审前必读）

本项目面向单店单人、轻量查价场景，以下三原则贯穿全部设计决策。**评审时若看到"为什么不XXX"，请先对照三原则——大概率是刻意不做而不是漏掉。**

**原则一：查价工具，不做收银**
做的是「这个多少钱」，不是「收你多少钱」。
→ 购物车仅合计看总价，不接支付、不生成订单、不留流水。加购即用即走，App 退出购物车自然清空。「结账」按钮仅模拟展示，不是真实支付。

**原则二：能自动绝不问用户**
店主不是技术人员，更不是系统管理员。系统能判断的路径不弹窗让用户选，能静默处理的操作不推送通知让用户确认。
→ 冲突自动覆盖、数据库损坏自动恢复、条码一致自动合并、降级无感切换。用户只需要知道结果，不需要参与决策。

**原则三：轻快无感，扫完就走**
交互节奏：扫一下、看一眼价格、关掉。不强留痕迹、不做持久化负担。
→ 购物车纯内存态、不记浏览历史、不追踪操作日志。一切设计以「减少停留时间」为目标。

**原则四：确定性规格，不给 Agent 留猜的空间**   [确定性补丁 v4.4]
AI Agent 写代码时能可靠地完成「看得见的 80%」，但会在「看不见的 20%」处悄悄崩——不是模型不够聪明，是规格不够精确。
→ 关键实现细节必须精确到 Agent 无法自由发挥的程度。杜绝「自动生成」「按规则拆分」「AI 辅助判定」等模糊描述，必须给出具体算法、库名、参数、输入输出示例。
→ 凡是 Agent 可能产出多种合理实现的地方，规格必须收窄到唯一解。
→ 评审优先检查：实现是否与规格精确一致，而非仅「看起来合理」。

### 设计要点

- **商品管理工具**：核心是查价，不是收银。不做支付、不记流水、不生成订单
- **购物车仅为合计**：加购后看总价，模拟结账展示清单+总额，[关闭并清空] 一步完成
- **查价优先**：扫码/语音/AI/手动搜索四通道查价，AI 识别结果需用户确认后才加入购物车
- **管理模式**：单身份设计，日常普通模式（查价/加购）；连击标题 5 次 → PIN 进入管理模式，可管理商品和修改配置
- **AI 可选**：AI 是增强输入通道，不是运行前提。无 AI 时降级为搜索+手动模式
- **离线可用**：商品数据全量存本地 SQLite（WAL 模式），无网也能查价
- **三层数据**：N1 家庭服务器（主存储+AI配置下发）→ 本地 SQLite（始终可用）→ WebDAV（手动备份恢复）
- **明确单写源**：N1 在线时以 N1 为权威源，本地修改推送至 N1；N1 离线时本地写入，重连后推送。冲突以 updatedAt 时间戳自动覆盖（时间比较基于 UTC，`new Date(updatedAt).getTime()` 毫秒值比较）  [确定性补丁 v4.4]
- **减少决策负担**：能替用户判断的尽量替用户判断，能自动处理的尽量自动处理——不因为"技术上可以问用户"就把抉择推给用户。冲突覆盖、数据库恢复、条码去重等均走静默自动策略

### 5.5 分类（预设10种）

零食 / 饮料 / 粮油 / 调味 / 日化 / 生鲜 / 冻品 / 烟酒 / 日用 / 其他

### 5.6 软删除   [确定性补丁 v4.4]

isDeleted=true，禁止物理删除。新增同名+同规格商品时恢复条目而非新建。

**查询过滤**：所有对 product 表的 SELECT 查询（商品列表、搜索、查价、去重检测等）必须在 WHERE 子句中添加 `AND isDeleted = 0`，确保已删除商品不出现在任何用户可见结果中。管理模式可提供「查看已删除」入口单独查询 isDeleted=1 的记录。

### 5.7 重复检测   [确定性补丁 v4.4]

条码一致 → 直接判定重复。名称相似度 ≥ 90% + 售价/规格至少一项一致 → AI 辅助判定。命中后列表展示，管理模式中可选择合并或确认非重复。

**相似度算法**：Levenshtein 距离 / max(len(a), len(b))，归一化至 0~1。比较前先 strip 并转全小写，忽略括号内容（"(500ml)" 等包装规格后缀不影响名称比较）。

## 六、中文搜索方案

### 6.1 FTS5 分词策略

问题：FTS5 默认分词器不做中文分词，"可乐"搜不出"百事可乐"。
方案：保存商品时 JS 层自动分词——将商品名/别名按单字拆分并空格连接，存入 searchText 字段供 FTS5 索引。

示例：「百事可乐」→「百 事 可 乐」，搜索"可乐"匹配成功。

**分词函数 `tokenizeChinese(text: string): string` 确定性规格**   [确定性补丁 v4.4]

- **CJK 字符范围**：仅拆分以下 Unicode 区间的字符，每个字符独立为一个 token：
  - CJK Unified Ideographs: `U+4E00` ~ `U+9FFF`
  - CJK Extension A: `U+3400` ~ `U+4DBF`
  - CJK Compatibility Ideographs: `U+F900` ~ `U+FAFF`
- **非 CJK 字符**（英文、数字、标点、空格等）：保持原样，连续非 CJK 字符合并为一个 token
- tokens 之间用单个空格连接，返回一个字符串
- 空字符串输入返回空字符串

**确定性输入输出示例**：

| 输入 | 输出 |
|------|------|
| `"百事可乐"` | `"百 事 可 乐"` |
| `"可口可乐500ml"` | `"可 口 可 乐 500ml"` |
| `"农夫山泉(550ml)"` | `"农 夫 山 泉 (550ml)"` |
| `"你好,世界"` | `"你 好 , 世 界"` |
| `""` | `""` |

**FTS5 索引同步**   [确定性补丁 v4.5]

每次对 product 表执行 INSERT / UPDATE（涉及 name/aliases 字段变更时）/ DELETE 时，必须同步维护 product_fts 虚拟表。**product 表写入和 product_fts 表写入必须在同一个数据库事务内完成**：
- INSERT → BEGIN TRANSACTION; INSERT INTO product; INSERT INTO product_fts; COMMIT;
- UPDATE → BEGIN TRANSACTION; UPDATE product; DELETE FROM product_fts WHERE id=?; INSERT INTO product_fts; COMMIT;
- DELETE → BEGIN TRANSACTION; DELETE FROM product_fts WHERE id=?; DELETE FROM product; COMMIT;

### 6.2 搜索流程（查询端与写入端分词对称）   [确定性补丁 v4.4]

写入端：保存商品时 JS 层调用 `tokenizeChinese()` 将 name+aliases 按单字拆分，空格连接存入 searchText（如「百事可乐」→「百 事 可 乐」）。

查询端：用户输入文字后，**调用与写入端完全相同的 `tokenizeChinese()` 函数**做单字拆分，转为空格分隔的查询词后再传入 FTS5 MATCH 语句（如用户输入「可乐」→ tokenize → 查询「可 乐」）。

**FTS5 查询特殊字符转义**   [确定性补丁 v4.5]

FTS5 MATCH 语法保留字符：`" ) ( - : ^ ~`（关闭引号、括号、连字符、冒号、帽子、波浪号）。查询词中包含时，将该 token 整体用一对双引号包裹：如 `(550ml)` → `"(550ml)"`。

**前缀通配符 `*`**   [确定性补丁 v4.5]
`*` 是 FTS5 前缀查询操作符，**不得**放入双引号内部，必须保留在引号右侧外部。正确语法：`"可" "乐"*`（匹配"可乐""可乐大瓶""可乐罐装"等前缀）。仅末尾位置的 `*` 保留为通配符；非末尾位置的 `*` 作普通字符，放入双引号内或直接剔除。

权重排序：精确匹配 name > alias 匹配 > pinyin 匹配 > searchText 模糊匹配；在售 > 缺货。

searchText 模糊匹配档：优先展示连续字命中（如"可乐"两字相邻出现），散字命中（"可""乐"分散在不同位置）排在后面。

**排序后处理**   [确定性补丁 v4.5]
搜索结果为「精确匹配 > alias 匹配 > pinyin 匹配 > searchText 模糊匹配」四个档位，同时「在售 > 缺货」。多档命中时先按档位排序，同档内按商品名称字典序。排序不依赖时间戳或外部评分算法，不引入 TF-IDF/BM25 等额外排序。

## 七、AI 引擎（可选）

### 7.1 降级逻辑

```

  ├─ 有 AI 配置且 API 可达 → 聊天模式（AI 驱动）
  └─ 无 AI 配置或 API 不可达 → 搜索模式（本地 FTS5 直搜）
```

### 7.2 AI 模式行为

**System Prompt 核心**：
```
你是 PStore 商品查价助手。
职责：理解自然语言（查价/数量），匹配商品库。
做法：匹配商品库（名称/别名/拼音/模糊），输出结构化 JSON。
约束：不确定时列候选项；回复简洁≤3句；仅在售商品可选。
```

**上下文注入**：购物车快照 + 当前模式（普通/管理）+ 最近 8-10 轮对话

**最大对话轮数**   [确定性补丁 v4.4]
上下文窗口最多保留最近 10 轮对话。超过时 FIFO 丢弃最旧轮次。每"轮"定义为一次用户输入 + AI 回复的组合。搜索模式不适用此限制。

**输出格式**：
```json
{ "action": "addToCart"|"search"|"ambiguous"|"notFound",
  "productId": "...",
  "quantity": 1,
  "message": "已找到可乐 ×2",
  "confidence": 0.85 }
```

### 7.3 搜索模式行为

输入文字 → FTS5 匹配 searchText/name/aliases/pinyin → 按权重排序 → 渲染商品卡片列表。

### 7.4 保护机制与纠错

- RAG Top K 20，不全量注入商品库
- productId 本地校验，不存在时拒绝加购
- AI 草稿卡 60 秒过期变灰，仍可点击确认
- 相同输入 5 分钟内复用缓存
- 中文数字预拦截（两瓶→2、半打→6）
- **用户可随时打断**：AI 流程中任何时刻可切回手动搜索
- **AI Key 本地加密缓存**：N1 短暂故障时可临时直连 AI，不必被迫降级
- **纠错出口**：拍照候选列表底部加「以上都不是→手动搜索」按钮；语音松开发送前可滑动取消

## 十、数据存储与同步

### 10.1 三层策略

| 层 | 条件 | 行为 |
|----|------|------|
| ① N1 云服务 | 配置地址且可达 | 权威数据源；自动拉取 AI 配置 + 全量同步商品；本地变更实时推送 |
| ② 本地 SQLite | 始终运行（WAL 模式） | 离线可用；收到 N1 数据后写入本地 |
| ③ WebDAV | 手动触发 | 始终可配置，用作数据备份与恢复，不参与实时同步 |

### 10.2 同步冲突合并

**单写源模型**：N1 在线时，N1 为权威源。本地编辑商品后推送至 N1，N1 合并存储。

**冲突检测与自动覆盖**：所有商品带 updatedAt 时间戳。同步时比对本地与 N1 的时间戳，以较新者为准自动覆盖，不做弹窗抉择：

```
if (N1.updatedAt > local.updatedAt)
    use N1
else
    keep local
```

无字段级 merge。单店单人场景下不存在同时编辑同一商品的可能，自动覆盖无需用户介入。

**重连恢复时序**：先推送本地未同步变更 → 服务端自动按时间戳合并 → 再全量 sync 拉取最终结果。确保本地离线修改不丢失。

### 10.3 数据库损坏恢复

App 启动时校验 SQLite 完整性（`PRAGMA integrity_check`）。若损坏：
- N1 可达 → 静默自动从 N1 全量拉取恢复，通知用户「数据已从云端恢复」，无需确认
- 单机模式（N1 不可达）→ 自动尝试从 WebDAV 最近备份恢复
- 两者均不可用 → 新建空库 + 告知「数据已损坏，请连接 N1 或配置 WebDAV 恢复」

WebDAV 恢复前先校验下载到的文件能否正常解析（能打开、表结构完整），校验通过再覆盖本地数据库。

### 10.4 Schema 迁移   [确定性补丁 v4.4]

数据库自带版本号字段 `schema_version`。App 启动时检测版本，自动执行增量迁移脚本（建新表、加字段、建索引等）。首次上线 version=1，之后每改数据模型升版本号并写迁移脚本。

**迁移脚本组织**：所有迁移脚本集中放在 `src/db/migrations/` 目录下，文件命名格式 `v{version}.ts`（如 `v2.ts`、`v3.ts`）。每个文件导出 `async function migrate(db: SQLiteDatabase): Promise<void>`。启动时从当前版本+1 开始顺序执行至目标版本号。

### 10.5 N1 云服务 API

极简 REST，Docker 部署：

```
POST /api/config/get     → 返回 { apiUrl, apiKey, textModel, visionModel }
POST /api/config/set     → 设置 AI 配置（需 PIN 密码）
POST /api/products/sync  → 全量拉取商品列表
POST /api/products/push  → 推送本地变更（新增/编辑/删除），附带 updatedAt 时间戳
```

### 10.6 切换状态

- 已连接 N1：绿色云图标 + 「已连接」
- N1 不可达：灰色云图标 + 「本地模式」
- WebDAV 模式：蓝色云图标

### 10.7 配置入口

顶栏 ☁️ 点击 → 配置中心：
- **N1 服务地址**（输入框，含端口）
- **WebDAV 配置**（URL / 账号 / 密码 / 测试连接 / 导出 / 恢复）——始终可配置
- **AI 配置**（API 地址 / Key / 文本模型 / 视觉模型）
  - N1 在线时从服务端拉取，本地加密缓存一份（N1 短暂断网时可临时直连）
  - 单机运行时手动编辑

**条码一致**：直接判定重复，静默自动合并——保留 updatedAt 较新的字段，旧商品名自动写入别名后软删除，无需用户操作。

**仅名称相似（≥ 90%，无条码或条码不同）**：左右并排 A/B 卡片 + [确认非重复] [合并]。合并时逐字段选择保留值，被合并商品名写入别名后软删除。

### 12.5 散装商品快捷入口

> 散装标签是用户主动点击、意图明确，跳过确认卡片是刻意设计的快捷路径，区别于 AI/扫码的自动识别结果（后者需要确认防误判）。

管理模式中可编辑散装快捷标签列表（新增/删除/排序）。

**存储方式**   [确定性补丁 v4.5]
散装标签列表采用运行时本地存储（非编译时常量），支持用户在管理模式中增删改排序。方案：SQLite 单表 `CREATE TABLE loose_goods_labels (id INTEGER PRIMARY KEY AUTOINCREMENT, label TEXT NOT NULL, sort_order INTEGER)` 或 AsyncStorage JSON 数组 `AsyncStorage.setItem('looseGoodsLabels', JSON.stringify(labels))`，与 N1 地址等用户可编辑的本地配置走同一套机制。

### 12.6 清空商品库

仅管理模式可用。点击后弹出全屏二次确认：
- 显示「将软删除全部 N 件商品」
- 要求手动输入「确认删除」四个字
- 确认后执行软删除（isDeleted=true），可从 N1 或 WebDAV 备份恢复

## 十四、运维

### 14.1 性能指标

- **性能指标**：冷启动 < 2s（先渲染骨架屏，商品数据异步加载）、搜索响应 < 300ms

### 14.2 错误处理策略   [确定性补丁 v4.4]

- **数据库操作失败**：SQLite 写入/读取失败时，Toast 提示"操作失败，请重试"，不静默吞错。连续 3 次失败后提示"数据库异常，请重启应用"。
- **网络请求失败**：N1 同步/AI API 超时或不可达时，静默降级至本地模式，不弹错误提示。超时时长：N1 同步 5s，AI API 10s。
- **崩溃恢复**：SQLite WAL 模式自带崩溃恢复。app 启动时执行 `PRAGMA integrity_check`，若失败则从最近 WebDAV 备份恢复；无备份则重建空库并提示用户。
- **AI 错误响应**：AI 返回格式无法解析时，降级为本地 FTS5 搜索，不重复请求 AI。
- **网络质量指示**：顶栏状态区显示网络类型 + AI 延迟色标（绿 < 1s / 黄 1-3s / 红 > 3s）
- **数据导出标准化**：CSV UTF-8 with BOM、日期 ISO 8601

## 十七、已知限制（当前版本不做）

- 不支持多设备同时在线协作（当前为单设备场景，多设备同步为后续路线图；届时 N1 API 需补 device_id 字段区分变更来源）
- 不接入微信/支付宝等支付通道
- 不生成销售记录、订单流水、日结对账
- 不做库存数量追踪（仅做有无状态标记）
- 不做赊账、套餐拆分、收银撤销等交易场景
- 管理模式不设闲置超时（仅主动退出）——单店单人单设备场景下，自动踢出是打断而非保护

> **经多轮评审讨论后明确排除的建议（归档备查）**：字段级冲突合并（单设备无并发）、同步窗口期风险（单设备不构成威胁）、WebDAV 版本链与完整性校验体系（备份量极少，手动冷备已够）、多表联动写放大优化（商品量小、编辑频率低）、FTS 排序长期不可控（1 万以内 + 连续命中优先规则已覆盖）、三通道仲裁层（不会同时触发）、纠正闭环学习机制（千条手动纠正成本可忽略）、测试策略与崩溃监控体系（单人小项目，正式体系为过度工程）。以上建议均基于「多用户/多端/大规模」假设提出，与单店单人单设备的实际场景不匹配。
