# PStore V4.1 规格书复审

v4.1 是一次认真的回应版本——变更历史里列出的 11 项修正，我逐条核对后，绝大多数确实落地了，而不是停留在"已知问题"的口头承诺上。下面按原来的五个维度复核，重点放在「修复是否到位」「是否引入新问题」「哪些之前标记的高风险项仍然没动」。

## 一、功能边界遗漏 —— 复核结果

**已解决**：开篇新增的"重要声明"和文末新增的「十七、已知限制」是这版最值得肯定的改动——把"结账不生成记录""不做库存数量追踪""不接支付""不做多设备协作"全部从"看起来像遗漏"转成"明确声明的非目标"。这比补功能本身更重要，因为它消除了规格书内部的预期落差，后续开发和用户期待都有据可依。PriceHistory 表（5.2）补齐了，解决了之前"11.2 提到价格曲线但数据模型没有对应表"的内部矛盾。AI/拍照/语音的纠错出口（7.4、8.2、9）、扫码无匹配时的 PendingItem 暂存机制（5.3、8.1）都按建议落地了，而且 PendingItem 这个设计比我原来的建议更好——它不只是"提示无匹配"，而是把未知条码变成一个可追踪、可在管理模式批量转正的数据实体，这是个加分项。

**新引入的小缺口**（风险：低）：PendingItem 表（5.3）只有 barcode 和 scannedAt，没有约束条码唯一性或重复扫描计数字段。如果同一个未录入条码被反复扫描（店员当场扫不出来会忍不住多扫几次），目前的设计会不会建多条 PendingItem 记录、堆出一堆重复条目？建议给 barcode 加唯一约束，重复扫描时只更新 scannedAt（或加一个 scanCount 自增），管理模式里转正时也更清爽。

**之前提的"现场改价/抹零"，这次我主动收回**：既然规格已经明确"购物车仅为合计看总价、不生成任何记录"（即没有真实交易发生），现场改价这个需求本质上是冲着真实收银场景去的，在当前的纯展示定位下确实没有必要存在了，这点之前的建议在新定位下不成立，不必处理。

## 二、技术风险点 —— 复核结果

**已解决**：样式方案敲定为 NativeWind v4，消除了"二选一悬而未决"的流程风险。中文分词问题给出了具体方案（六、单字拆分 + searchText 字段），这是个合理且工程成本低的 trigram-like 方案。冷启动指标补了实现路径（骨架屏 + 异步加载）。扫码兜底加了手动输入条码框（8.1），低端机扫码失败时不再卡死在"无匹配提示"这一层。

**部分解决，需要补充一句**（风险：低中）：searchText 用的是单字拆分（"百事可乐"→"百 事 可 乐"），这能解决"搜不出"的召回问题，但中文单字本身信息密度低，容易在模糊匹配层带来噪声——比如搜"可乐"，"可"和"乐"作为独立 token 可能命中很多语义无关但凑巧含同字的商品（"可比克薯片""乐事薯片"），尤其商品库到几百上千规模后这个噪声会更明显。6.2 的权重排序（精确 > 别名 > 拼音 > searchText 模糊）方向是对的，但建议补一句具体规则：searchText 命中只在前面三档都查不到候选时才启用，且优先展示"连续字命中"（如"可乐"两字相邻）而非"字符都出现但顺序打散"的结果，否则模糊层会显得很不智能。

**仍未解决**（风险：中，技术债，非阻断项）：
- React Native 0.76 + Expo SDK 52 的新架构（Fabric/TurboModules/Bridgeless）兼容性问题，这版规格依然没有提到任何版本锁定或依赖验证计划。这条建议作为开发启动前的第一步动作清单单独列出，不一定要写进规格书正文，但不能遗漏。
- 测试策略和可观测性（崩溃监控、核心降级路径的测试覆盖）依然完全没有提及。考虑到这个 App 涉及相机、本地数据库、AI 降级、三层同步多种状态组合，没有测试策略和崩溃上报，后期排查"为什么某台设备搜索不出商品"这类问题会很被动。

**新引入的待澄清点**（风险：低中）：技术栈里把扫码引擎从泛泛的 vision-camera 改成了"使用 MLKit 原生扫码引擎"（二、8.1）。如果产品只面向 Android，这个改动是合理的性能优化（MLKit Barcode Scanning 比自定义 frame processor 更省电更稳）；但 react-native-vision-camera 是跨平台库，MLKit 并不是 iOS 的原生方案（iOS 上对应的是 Apple Vision Framework）。规格书全文没有明确限定平台（虽然之前的项目背景是 Android 应用），建议在技术栈一节补一句平台范围说明，避免实现时才发现 iOS 分支需要单独适配。

## 三、三层数据策略缺陷 —— 复核结果（这是这版改动最实质的部分）

**全部三个高风险项都已解决，而且方案具体可执行**：
- updatedAt 时间戳 + 单写源模型（一、10.2）：明确了"N1 在线时 N1 为权威源，冲突以时间戳较新者为准，双方都改过时弹窗让用户选择保留本地/服务端"，这把之前"静默覆盖"的最大隐患堵上了。
- 重连恢复时序（10.2 末段）：明确写出"先推送本地未同步变更 → 冲突弹窗 → 再全量 sync"，解决了之前最担心的"先 sync 覆盖本地未推送变更"这个顺序陷阱。
- WebDAV 互斥问题：彻底解除，10.1/10.7/4.5 都改成"始终可配置"，灾备配置不再依赖"N1 已经先掉线才想起来配"这种事后诸葛亮式的设计。

**额外加分**：10.3 数据库损坏恢复、10.4 Schema 迁移版本号机制，这两条原本不在三层数据这一维度的提问范围内，但属于我上一轮额外建议的内容，也都补上了，而且方案是可落地的（PRAGMA integrity_check、schema_version 字段 + 迁移脚本），不是空话。

**值得追加验证的边界情况**（风险：低，已大幅降低但建议显式测试）：之前提到"软删除 vs 同名恢复"在多设备并发下谁赢的问题，现在用 updatedAt 时间戳机制理论上能自然覆盖（同一条记录，谁的修改时间晚谁赢），但规格书没有显式把这个场景列为测试用例。建议在开发阶段把"设备 A 软删除商品 X 的同时，设备 B 新增同名同规格商品触发恢复逻辑"作为一条专门的集成测试用例，而不是依赖通用冲突机制"应该能处理"的假设。

## 四、管理模式设计评估 —— 复核结果（两个高风险项仍未处理，需要重点提醒）

**已解决**：
- 可发现性问题：抽屉底部新增"管理模式"快捷入口（11.2 方式二），保留连点手势的同时降低了认知门槛，安全性没打折（仍需 PIN）。
- PIN 遗忘无法恢复：11.3 补了"通过 N1 后台生成一次性恢复码重置"，这条解决得很干净。

**仍未解决，且是上一轮我标记为"高风险"的两项，建议优先处理**：

1. **管理模式闲置超时缺失**（风险：高，原样保留）。11.2 退出方式依然只有"再次连点标题"或"点抽屉里的退出按钮"或"App 重启"，没有任何自动超时或锁屏/切后台自动退出的机制。便利店柜台手机/平板被多人接触是常态，店主进管理模式后离开柜台几分钟，只要 App 进程没被系统杀掉，期间任何人都能新增/删除商品、改 N1 地址、改 AI Key。这条在上一轮就是高风险项，这次的修正清单里没有提到它，应该是被遗漏了，建议补一条：App 切到后台或锁屏时自动退出管理模式，加上比如 5-10 分钟无操作自动退出兜底。

2. **清空商品库依然没有二次确认**（风险：高，原样保留）。11.1 把"清空商品库"列为管理模式可用操作，但全文（包括新增的 11.x、12.x 各节）都没有出现任何确认弹窗或二次校验的描述，对比同样有破坏性的批量管理（12.3）好歹还有逐行 CheckBox 选择，"清空"这种一键全删的操作反而保护最少。建议补充：强制二次确认弹窗，文案写明"将软删除全部 N 件商品，可从 N1/WebDAV 恢复"（利用 5.6 的软删除机制降低用户恐慌，但弹窗本身不可省），必要时清空前要求重新输入 PIN。

这两条建议在评审清单里被跳过了，不确定是疏漏还是优先级排序问题，但鉴于这是面向真实小店主使用的工具，建议在下一版里补上，成本很低（纯前端交互逻辑，不涉及数据模型变更）。

## 五、架构扩展性 —— 复核结果（评估方式需要调整）

这一维度上一轮的批评本质是"规格书没说清楚现在的架构能不能撑住支付/多设备"，这次的回应方式不是去补架构，而是在「十七、已知限制」里明确声明这两件事现在都不做、"多设备同步为后续路线图"。这是合理且诚实的产品决策——不需要为不存在的需求预先过度设计，我认可这个处理方式，原来的"高风险"标签在当前范围下应该解除。

但需要留一句面向未来的提醒，不算这版的缺陷：如果"多设备同步"真的进入路线图，10.5 的 N1 API（sync/push 两个端点）目前仍然没有 device_id 字段，无法区分变更来源；10.2 新增的 updatedAt 冲突机制能较好支撑"轮流使用、非同时在线"的多设备场景，但如果未来要做真正的"多设备同时在线、互相实时感知对方变更"，现在纯 REST 轮询的方式仍然撑不住，需要补设备标识 + 增量同步 + 推送通道（WebSocket/SSE）。这条不需要现在动，只是建议在「十七、已知限制」里加一句"未来若支持多设备协作，需重新设计同步 API"，提前给后续接手的人留个路标。

支付接入这条同理，已经明确排除在范围外，不需要现在评估架构改动成本。

---

## 复审结论

修正幅度很大，质量也高——尤其是三层数据冲突机制（维度三）和中文搜索方案（维度二），都是给出了具体可落地的方案而不是泛泛带过。「十七、已知限制」这个新增章节本身是个很好的工程习惯，建议以后每次范围变化都维护这张表。

唯一需要拉回来重点处理的是维度四里那两项：**管理模式闲置超时**和**清空商品库二次确认**。这两条在上一轮就被标记为高风险，这次的修正清单里没有出现，而且都是改动成本很低、一旦上线后出现真实数据损失就很难挽回的类型，建议作为 v4.2 的第一优先级补上。
