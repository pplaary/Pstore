作为资深 React Native 架构师，针对这份《PStore V4 规格书》进行系统性项目评审。这份规格书充分体现了“本地优先、触控关怀、敏捷降级”的实用主义设计理念，但在便利店高频、复杂的真实业务场景下，架构设计仍存在一些关键的“硬伤”与隐患。

以下是从五个维度展开的深度评审结论与优化建议：

---

## 一、 功能边界遗漏评估

### 评审结论：风险等级——**中**

规格书在核心链路（查价 $\rightarrow$ 加购 $\rightarrow$ 结账）的设计上逻辑闭环，但在便利店实际作业场景中，存在明显的**体验断点**和**管理盲区**。

* **无条码/散装商品处理缺失**：便利店常见塑料袋、热餐、散装零食等无条码商品。目前过于依赖“📷 相机扫码”和“AI 语音”，若无 AI 配置且商品无码时，普通模式下通过本地直搜加购的路径不够直观（缺乏虚拟分类键盘或快捷标签）。
* **普通模式下的“未知条码”死锁**：当系统处于“普通模式”时，店员若扫到一个商品库未录入的新条码，系统提示“无匹配”，由于普通模式无法新增商品，该商品将彻底无法在当前收银流程中处理，直接导致收银中断。
* **结账不留痕的财务风险**：虽然定位是“智能查价助手”，但既然提供了“去结账”并清空购物车的功能，若完全不记录任何流水的历史快照，店长在做日终对账或盘点时，将无法追溯当天的营业概况。

### 架构师建议：

1. **增加未知条码暂存区**：扫描未录入条码时，允许普通模式下以“未知商品-固定临时价”临时加购，并自动在本地生成一条“待补全商品”记录，供后续管理模式一键转化。
2. **增设本地轻量流水日志**：结账时虽不生成复杂的订单系统，但建议在 SQLite 中异步写入一行极简的流水日志（时间、总金额、商品 ID 列表），仅用于管理模式下的“今日营收看板”及 CSV 导出。

---

## 二、 技术栈风险点分析

### 评审结论：风险等级——**中**

选型紧跟前沿（React Native 0.76 + Expo 52），但在组件库组合及特定平台适配上存在潜在的性能与编译陷阱。

* **RN 0.76 新架构（New Architecture）兼容泥潭**：RN 0.76 默认启用了新架构（TurboModules 和 Fabric）。`react-native-vision-camera` 在新架构下的 Frame Processor（用于扫码/拍照识别）需要依赖复杂的物理原生桥接或特定版本的插件（如 Worklets）。若处理不当，极易导致低端低配安卓机型上频繁闪退。
* **UI 框架双选冲突**：技术栈中同时出现了 `NativeWind / Tamagui`。这两个框架的设计哲学和编译机制完全不同（Tailwind 样式原子化 vs 运行时/编译期组件化 Token 驱动）。两者混用不仅会使包体积暴增，还会导致视觉 Token（3.1 节）在底层实现时产生样式冲突。
* **SQLite FTS5 的中文分词缺陷**：`expo-sqlite` 原生携带的 FTS5 模块，在默认情况下**不支持中文智能分词**（它会将中文当成一整串字符或按标点符号断句）。在 1000+ 商品规模下，直接输入“可乐”可能根本搜不出“百事可乐”，除非在存入 `name` 和 `aliases` 时手动在 JS 层进行“空格分词预处理”（如将“百事可乐”存为“百 事 可 乐”）。

### 架构师建议：

1. **明确统一 UI 框架**：严禁混用，建议在当前轻量级场景下精简为单用 `NativeWind v4`，以保持轻量和高开发效率。
2. **JS 层中文分词介入**：由于没有原生中文字典支持，商品保存时，除了生成拼音首字母，还必须在本地利用轻量级 JS 分词逻辑（或直接按单字加空格补全），以确保 FTS5 模糊搜索的命中率。

## 三、 三层数据策略缺陷

### 评审结论：风险等级——**高**

这是目前架构中**最容易导致数据混乱和丢失**的模块。多端读写与离线状态切换时缺乏严格的状态机管理。

* **双向同步的冲突合并（Conflict Resolution）策略真空**：规格书提到“本地变更实时推送至 N1”。然而，如果 N1 暂时断连，店员在本地修改了 A 商品的价格为 5 元；与此同时，另一个设备在 N1 恢复前将 N1 端的 A 商品价格改为了 6 元。当本地重新上线执行 `POST /api/products/push` 时，会发生盲目覆盖，缺乏基于时间戳（`updatedAt`）或三方对齐的冲突解决机制。
* **WebDAV 隐藏导致的灾难性兜底失效**：规格书规定“N1 在线时隐藏 WebDAV 配置”。这意味着当有网络时，用户无法配置 WebDAV。一旦 N1 硬件损坏或永久离线，App 切换到单机模式，此时 WebDAV 虽然显现，但由于之前从未配置过，根本无法起到“自动兜底同步”的作用。
* **本地覆盖与增量同步的混乱**：从 WebDAV 恢复数据是全量覆盖本地 SQLite，还是增量合并？如果在本地模式下用 WebDAV 恢复了历史数据，随后再次连上 N1，本地被动触发拉取 N1 数据，会直接造成数据错乱或历史数据回滚。

### 架构师建议：

```
[本地变更] ──> 检查更新时间(updatedAt) ──> 采用最新(Last-Write-Wins)
                                              │
                      ┌───────────────────────┴───────────────────────┐
                      ▼                                               ▼
            【N1 在线模式】                                    【单机模式】
    (全量同步拉取 / 实时异步推送)                         (允许配置 WebDAV 作为独立备份)

```

1. **引入 Last-Write-Wins (LWW) 策略**：所有数据变更（N1 与本地）必须强制校验 `updatedAt` 时间戳，服务器端应提供增量同步（Delta Sync）接口，而非只有全量拉取。
2. **WebDAV 降级为独立冷备**：解除 N1 与 WebDAV 的互斥关系。WebDAV 应作为全场景下的“定时冷备份”手段（例如每周夜间自动导出一个 CSV/SQL 密文文件到云端），而不是与 N1 交替运行的实时同步层。

## 四、 管理模式设计评估

### 评审结论：风险等级——**高**

为了追求极简的单身份设计，牺牲了实体店高频高压作业环境下的**基础安全性**。

* **无时效限制的 PIN 码是巨大的安全漏洞**：规格书写道：“PIN 无时效限制，持续有效，直到主动退出”。在便利店日常场景中，店长进入管理模式修改完价格后，极易因突发客流而将手机随手扔在收银台。由于没有前台无操作超时锁定，任何顾客或临时雇员都可以任意查看、导出、甚至执行“清空商品库”等毁灭性操作。
* **高危操作缺乏二次防御**：侧滑抽屉中向全员开放了“清空商品库”的危险入口，且未提及任何诸如“输入 ERASE 确认”或双重验证的防误触设计。

### 架构师建议：

1. **引入前台自动超时熔断**：管理模式必须增加无操作计时器（建议 3-5 分钟），超时未触控屏幕自动降级回“普通模式”。
2. **高危操作引入破坏性确认门槛**：点击“清空商品库”或“软删除全库”时，必须强制弹出独立的全屏遮罩，要求用户手动输入“确认删除”四个字或重新校验 PIN 码。

---

## 五、 架构扩展性评估

### 评审结论：风险等级——**中**

当前架构完全服务于“单机/离线查价”的特定靶心，向商业化收银转型的技术债较高。

* **接入聚合支付的阵痛**：目前结账流程“不生成任何记录”。未来若接入微信/支付宝原生 SDK 支付，当前纯 Managed 的 Expo 流程必须引入 `Custom Dev Client`（开发版客户端），并重构整个状态机——需要引入 `Order`（订单表）和 `PaymentTransaction`（支付流水表），当前的内存 Zustand 购物车数据无法保证在支付回调闪退时的事务安全性。
* **多设备共享 N1 的并发锁死**：目前的 N1 云服务 API 设计（`POST /api/products/push`）是粗暴的“推送本地变更”。如果有两台设备同时在店内扫码查价并修改状态，N1 服务端若没有行级锁或分布式锁，会导致数据库发生死锁或写入数据丢失。

### 架构师建议：

1. **解耦购物车与状态机**：在 Zustand 状态设计中，将“当前收银会话”与“商品基础库”彻底解耦，预留一个 `sessionID` 产生机制，以便未来能无缝对接订单流。
2. **N1 服务端向中间件靠拢**：如果后续有过多台设备协同的需求，N1 端的 Docker 服务应尽快放弃简单的文件流读写，改用具备事务支持的轻量级数据库（如 PostgreSQL 或配备了 WAL 模式的 SQLite），并由服务端负责生成自增的系统全局版本号（Revision Version）来控制多端多设备同步。

---

### 评审总结

PStore V4 的规格书整体而言是一份完成度很高、贴合特定硬件（如 Phicomm N1）环境的落地指南。建议在正式进入 RN 0.76 编码阶段前，**优先解决“三层数据流的同步冲突算法”与“管理模式的超时自动退出机制”**，这两点直接决定了该系统上线后的数据合规性与商用稳定性。
