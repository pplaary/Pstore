基于 v4.1 版本重新评审（）。这版已经比 v4.0 收敛很多，尤其是把“收银系统”彻底切掉之后，架构风险下降了一档，但同时引入了几个新的一致性与复杂度问题。

---

# 1. 功能边界遗漏

**结论：边界基本清晰，但“临时商品态 + 纠错闭环”仍不完整（中风险）**

这一版已经把系统严格限定为“查价 + 模拟合计”，不再涉及订单/支付，这一步是正确的，直接消掉了最大复杂度来源。但在真实便利店操作中，仍有几条链路不完整。

第一是“未知条码 PendingItem → 正式商品”的链路虽然存在，但缺少“批量收敛机制”。现在是单条扫码生成 PendingItem，如果连续扫多个未知商品，管理模式才统一处理，这会导致一种结构问题：数据在“无意义积累”，但没有自动归并或提醒策略。

第二是“AI / 扫码 / 搜索三通道结果的冲突优先级”仍然隐含。比如 AI 给出候选、扫码给出唯一匹配、手动搜索同时触发时，UI 如何收敛没有明确仲裁层。现在是 UI 驱动，而不是结果层驱动。

第三是“纠错闭环”仍偏弱。虽然有“忽略/手动搜索/以上都不是”，但没有形成持续学习机制（比如 alias 自动生成、错误映射记录）。长期使用后，系统不会变聪明。

---

# 2. 技术风险点

**结论：技术栈合理，但扫码与 SQLite 写路径仍是主要性能风险点（中风险偏高）**

相比 v4.0，这一版最大改进是：

* MLKit 原生扫码
* WAL 模式 SQLite
* FTS5 + searchText 分词优化
* NativeWind 替代样式体系

这些都降低了 RN 侧复杂度。

但仍有三个真实风险点：

### 2.1 vision-camera + MLKit 集成复杂度

虽然改为 MLKit，但 vision-camera 在 Expo SDK 52 下依旧属于“半裸模块”，EAS prebuild 复杂度没有消失。真正风险不是性能，而是：

* iOS / Android 构建一致性
* frame processor 插件兼容性
* Expo 升级锁死版本

### 2.2 SQLite 写放大问题

你现在引入了：

* Product
* PriceHistory
* PendingItem
* FTS searchText

写入路径变成“多表联动写”，尤其商品编辑会触发：

* product update
* price history insert
* FTS 更新

在低端 Android 上，短时间批量编辑会出现 UI thread 卡顿（不是查询问题，是写放大）。

### 2.3 FTS 中文分词方案的长期维护成本

searchText 单字拆分是“工程可用解”，但问题是：

* 精度依赖规则而不是语言模型
* alias/pinyin/searchText 三套权重叠加后不可解释性增加

短期没问题，长期商品规模上万后排序会变“不可控”。

---

# 3. 三层数据策略缺陷

**结论：一致性问题已修正方向正确，但冲突模型仍然偏弱（中风险）**

v4.1 相比 v4.0 最大进步是明确了：

* N1 为权威源
* 本地可写
* 冲突用 updatedAt + 弹窗解决

这已经是“可落地模型”。

但仍有三个结构性缺口：

### 3.1 时间戳冲突模型过于单一

只用 updatedAt = 最后写入胜出，会导致典型问题：

* 离线修改 A（价格）
* 在线修改 B（规格）
* 最后一次写入覆盖整条记录

字段级冲突仍然不存在，只能整条覆盖。

### 3.2 同步顺序隐含风险

当前流程是：

1. push local
2. 冲突处理
3. full sync

问题在于 full sync 是“状态覆盖式”，如果 N1 在 push 后短时间内再次变化，会被覆盖掉一次窗口期更新。

### 3.3 WebDAV 完全“非实时备份”定位是对的，但缺少验证机制

现在 WebDAV 只是 dump/restore，但没有：

* 备份完整性校验
* 版本链
* 最近可用快照索引

一旦恢复点不可靠，会变成“心理兜底，而不是工程兜底”。

---

# 4. 管理模式设计评估

**结论：可用性提升明显，但权限模型仍然偏“UI安全”，不是“系统安全”（中风险）**

这一版比 v4.0 最大改进：

* 增加侧滑入口
* PIN 恢复机制
* 明确抽屉入口
* 管理入口可发现

这些修正是关键的，说明已经从“隐藏入口设计”转向“可操作权限系统”。

但仍然有三个问题：

### 4.1 权限没有分级

现在只有：

* 普通模式
* 管理模式

但管理模式内部权限是全开的，这会导致：

* 清空商品库
* 修改同步配置
* 删除数据

全部属于同一等级风险操作。

### 4.2 清空商品库仍然缺少“不可逆保护层”

没有：

* 二次确认策略（强约束）
* 操作审计记录
* 延迟删除窗口

这类操作在真实环境属于最高风险行为。

### 4.3 PIN 仍然是“会话锁”，不是“操作锁”

PIN 解锁后整段时间信任状态持续，这意味着：

* 设备被解锁后可持续误操作
* 没有敏感操作再验证机制

---

# 5. 架构扩展性

**结论：当前版本明确拒绝收银/支付是正确决策，架构因此稳定，但未来扩展仍需重构（低风险/高潜在重构成本）**

v4.1 在这一点上其实做对了一件关键事情：**彻底切掉订单系统**。

这让系统从：

> POS系统
> 变成：
> 商品工具系统

复杂度下降一个数量级。

但问题在于，如果未来再扩展回支付/库存系统，会遇到“结构缺口已经被刻意清空”的情况。

### 5.1 当前缺失的领域模型

现在系统没有：

* Order
* Inventory movement
* Transaction log

这意味着未来如果接入支付：

* 需要从 Product 直接跳到 Payment
* 中间没有状态层

这是典型“断中间层架构”。

### 5.2 多设备扩展仍然弱一致

当前模型是：

* 单设备写
* N1 权威同步

如果未来变成多设备同时写，会直接失效，因为没有：

* 操作日志（event log）
* 冲突合并策略（CRDT 或 field-level merge）

### 5.3 当前架构的真实适用边界

这一版其实非常清晰地收敛到了一个边界：

> 单店单设备商品查价系统（弱同步）

在这个边界内，它是合理的。

一旦越过边界（多设备/支付/库存），需要重新引入领域模型，而不是在现有结构上补丁。

---

# 总体结论

v4.1 已经完成一次“正确的收敛”，主要变化是把系统从 POS 拉回到工具型应用，这一步是架构质量提升的关键点（）。

当前状态可以这样概括：

* 功能边界：基本正确，但纠错闭环不完整
* 技术栈：可落地，但扫码 + SQLite 写放大仍是主要风险
* 同步模型：已可用，但字段级冲突缺失
* 管理模式：可用，但权限模型偏粗
* 扩展性：短期稳定，长期需要重建领域层

如果只做 v4 目标（查价工具），这版已经接近可施工状态；如果未来要扩展成“商业级收银系统”，当前结构仍然需要一次“领域层重构”，否则会在扩展时出现硬断裂。
