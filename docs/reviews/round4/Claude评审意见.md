v4.4 是个方向性的大改动——上一轮"可以去开发了"是基于 v4.3 的自然语言规格说的，v4.4 这次把"原则四：确定性规格"立成了新的设计原则，把之前那些"自动分词""AI辅助判定"之类的模糊表述收窄成了具体算法、库名、参数、输入输出示例。这个方向本身是对的，尤其是面向 Agent 写代码这种场景，"规格精确到 Agent 无法自由发挥"确实是该补的课。

但这版文档末尾自己附了一份"第四轮评审指引"，把 P0/P1/P2 的检查清单也写进了规格正文，相当于自己给自己出题、还顺手定好了评分标准。这个做法我不会照单全收——清单能保证"有没有覆盖到某个话题"，但不能保证"覆盖的内容本身是不是对的"，所以我按它给的框架逐条核对，但结论是我自己独立验证出来的，不是按它的检查点打勾。核对下来，发现了两个真正的技术问题，其中一个还是文档自己最强调"必须精确到能直接编译"的那一类。

## P0 级核对（7 条）

P0-1（拼音）、P0-2（CJK 范围）、P0-3（searchText 先合并再分词）、P0-6（isDeleted 全局过滤）、P0-7（FTS5 索引同步，INSERT/UPDATE/DELETE 同步维护虚拟表，UPDATE 用先删后插，这是 FTS5 虚拟表的标准做法）——这五条描述具体、自洽、可以直接照着写代码，没有发现问题。

**P0-4（查询/写入同函数）和 P0-5（FTS5 转义）放在一起看，发现一个真正的内部矛盾**，这是这轮复审最重要的发现。6.1 节定义的 `tokenizeChinese` 规则是"连续非 CJK 字符合并为一个 token"，按这条规则，「(550ml)」这种全是非 CJK 字符（括号+数字+字母）且彼此相邻的字符串，应该整体作为**一个** token。但 6.2 节给的转义示例却写成「输入 `(550ml)` → tokenize → `"( 550ml )"`」——这里把左括号、550ml、右括号拆成了三个独立 token，直接违反了它自己两段之前刚定义的合并规则。Agent 写代码时会卡在这里：到底该信 6.1 的分词函数定义，还是信 6.2 给出的具体示例？这两者互相矛盾，没法同时满足。

更进一步，转义后的最终结果 `""(" 550ml "")""` 这串字符本身在语法上也站不住脚——这不是标准 FTS5 转义写法（标准做法是把含特殊字符的整个 token 用一对双引号包起来，比如 `"(550ml)"`），这种多层嵌套引号的写法照抄过去大概率会让 SQLite 在执行 MATCH 查询时直接抛语法错误，而不是被正确解析。这条建议改成：分词函数严格按 6.1 规则保持「(550ml)」为单个 token，转义规则简化为"该 token 含特殊字符时整体用双引号包一次"，去掉中间那个看起来像是手滑的拆分步骤。

## P1 级核对（5 条）

P1-1（UUID v4）、P1-2（UTC 毫秒值比较）、P1-3（错误处理策略）、P1-5（迁移脚本目录规范）——这四条都写得具体可执行，没有问题。

**P1-4（散装标签存储方案）有个实际会卡住生产环境的问题，建议提到 P0 级别重新处理**。规格写的是"散装标签列表为编译时常量，写入 `looseGoodsLabels.ts`，管理模式增删改通过编辑该文件完成（用户操作→写入文件→热重载生效）"——热重载（Fast Refresh）是 Metro/开发服务器提供的开发态能力，店主手机上跑的是已经打包好的 APK，没有开发服务器在背后监听文件变化，也没有运行时重新编译 TS 文件这回事。这意味着 12.5 节写明的"管理模式中可编辑散装快捷标签列表"这个功能，按当前存储方案在真机上根本跑不起来，不是"有几种合理实现都行"的 P1，是会直接导致功能失效的设计错误。建议改成运行时本地存储——加一张小的 SQLite 表，或者用 expo-secure-store/AsyncStorage 存一份 JSON 数组，跟其他用户可编辑的本地配置（比如 N1 地址）走同一套机制即可，成本不高。

另外，6.1 节的 FTS5 索引同步规则建议补一句："product 表写入和 product_fts 表写入必须在同一个数据库事务内完成"——目前的描述里两个表的写入是分开两步说的，没强调原子性，万一中途崩溃容易留下"商品改了但搜索索引没跟着改"的不一致状态，这点用一句话堵上就行，不算大改动。

## P2 级核对（4 条）

P2-1（Levenshtein 相似度，含忽略括号内容的预处理）、P2-2（PendingItem 转换不做自动推断）、P2-3（AI 对话轮数 10 轮 + FIFO）——这三条没问题。P2-4（排序后处理）里有一句话读起来语义不清——"搜索词与结果不产生 new Date 无关的时间排序"，这句大概率是想表达"排序不依赖时间戳"，但措辞本身有点像没整理干净的产物，建议重写成一句正常的话，不算逻辑错误。

## 结论

不能直接说"可以去开发"。这版整体方向和大部分补丁质量是真的好（CJK Unicode 范围给得很精确，pinyin-pro 参数、迁移脚本目录规范这些都是直接能抄的标准），但 FTS5 转义规则的内部矛盾、散装标签存储方案在生产环境不可行，这两个是会让 Agent 在实现阶段卡住或者写出跑不通代码的真问题，建议先改了再进 v4.5：转义规则按 6.1 的分词规则改成单层 token 包引号；散装标签存储从编译时常量改成运行时本地存储。这两处改完之后，这份规格在"确定性"这件事上才算真正达标。
