# PStore V4 规格书系统性评审

读完全文，V4 相对 V3 是一次大幅瘦身（聚焦查价而非全功能 POS），这个收缩本身是合理的，但收缩之后留下的边界和断点也更值得仔细推敲。以下按五个维度展开，每条结论标注风险等级并给出具体建议。

## 一、功能边界遗漏

- **"结账不生成任何记录"是整份文档里最大的功能空白**（风险：高）。4.3 明确写"确认后清空购物车，不生成任何记录"，意味着没有任何交易流水、没有日结对账、没有退货可追溯性。如果这是刻意的"轻量查价工具"定位，建议在设计理念章节明确写一句"本产品不做销售记录/对账，仅做实时计价"，避免店主用了一段时间后期望看到营业额统计而落空。哪怕不做完整订单系统，至少应该有一个本地"最近结账历史"的轻量日志（时间+总额+商品明细），成本很低但能堵住最常见的真实需求缺口。

- **价格历史曲线与数据模型自相矛盾**（风险：中）。11.2 提到"价格历史变化曲线，数据来源于价格变更记录"，但 5.1 的 Product 表里没有 priceHistory 这张表或字段，只有当前 price。这是规格内部不一致，需要补一张 PriceHistory（productId, oldPrice, newPrice, changedAt）表，否则这个功能在实现阶段会卡住。

- **没有"现场改价/抹零"能力**（风险：中）。便利店给熟客抹零、临时议价是高频场景，但购物车里商品的单价似乎锚定商品库标价，只有数量可调（4.3 只提到 ⊕⊖）。建议购物车行内允许临时改单价（不影响商品库标价，只影响本次结账），并在结账弹窗里显示"原价/实收"差额。

- **库存数量管理的范围声明不清**（风险：低中）。Product 只有三态状态（在售/缺货/待采），没有数量字段，这意味着加购时不会检查库存是否够卖。这可能是有意为之（定位是"查价"不是"进销存"），但应该在设计理念里明确写一句"不做库存数量追踪，仅做有无状态标记"，否则容易被理解为遗漏而不是取舍。

- **AI/拍照/语音识别错误后的纠错路径缺失**（风险：中）。拍照识别返回候选列表后，如果用户发现都不对，没有"以上都不是→手动搜索"的出口；语音识别错了，也没看到"重说/取消"的明确交互。这些是查价主流程上真实存在的小断点，建议在 6.4 保护机制里补一条"用户可随时打断 AI 流程切回手动搜索"。

- **数据库损坏的恢复路径完全空缺**（风险：中高）。第十四节提了本地数据库加密，但全文没有任何关于 SQLite 文件损坏检测/自动备份/从 WebDAV 或 N1 恢复的描述。既然已经设计了三层数据策略，损坏恢复应该是顺理成章的一环，建议补充：启动时校验数据库完整性 → 损坏时引导用户从 N1 重新全量拉取，或单机模式下从 WebDAV 恢复。

- **App 升级时的 SQLite Schema 迁移策略未提及**（风险：中）。一旦上线后再加字段（比如补 priceHistory 表），需要明确的迁移机制，建议补充版本号字段+迁移脚本表。

## 二、技术风险点

- **新架构（Fabric + TurboModules + Bridgeless）兼容性是这套技术栈最大的隐性成本**（风险：中高）。RN 0.76 起新架构基本成为默认形态，Expo SDK 52 同步跟进。这意味着 react-native-vision-camera、expo-sqlite 等关键依赖都必须确认其当前版本对新架构的支持是否成熟，部分第三方库在新架构下仍存在 interop 层兼容问题或调试工具链（Flipper 等）适配滞后的情况。建议在技术选型阶段就锁定每个关键依赖的具体版本号并做一次新架构下的最小可行验证，而不是假设"装上就能用"。

- **react-native-vision-camera 无法在 Expo Go 里跑，必须走 EAS Build / dev client**（风险：中，属于流程/团队协作成本而非功能缺陷）。这会影响日常开发联调效率，也意味着每次测试扫码功能都要走自定义构建，CI/CD 需要相应配置，建议在技术栈说明里明确写出这个前置条件，避免团队成员后期才发现。

- **expo-sqlite 的 FTS5 可用性需要显式验证，不能假设默认可用**（风险：中）。不同 Expo SDK 版本中 SQLite 编译时是否打开 FTS5 扩展存在变动历史，建议落地前先写一个最小用例（建一张 FTS5 虚表）验证可用性，不可用则需考虑 op-sqlite 等替代方案。

- **FTS5 在 1000+ 商品规模下，原始查询性能不是瓶颈，但中文分词是真正的风险点**（风险：中高，这是技术维度里最需要重视的一条）。FTS5 默认的 unicode61 分词器不做中文分词，对中文文本基本等同于"整段当一个 token"，无法很好支持子串/模糊匹配，这会直接影响 6.3 描述的"按权重排序（精确 > 别名 > 拼音 > 模糊）"效果——模糊这一档实际上可能名不副实。建议改用 FTS5 的 trigram 分词器，或继续依赖现有的 pinyin 字段 + LIKE 查询兜底，不要假设默认配置对中文友好。原始查询速度本身（不含分词问题）在千级数据量下完全不是问题，通常在个位数到几十毫秒级别，13 节定的 300ms 搜索响应目标是宽松的。

- **vision-camera 在低端安卓机上的扫码体验需要单独验证**（风险：中高）。小店常见机型偏低端（内存小、Camera2 API 实现质量参差），帧处理器（Frame Processor）做条码识别属于持续 CPU 占用操作，低端机上容易出现发热、掉帧、自动对焦慢等问题，店内灯光反光在便宜摄像头上也更容易导致识别失败。建议针对目标机型做一轮真机测试（尤其是 2-3 年前的千元机），并设计降级方案（例如手动输入条码作为兜底，而不仅是"无匹配提示"）。

- **样式方案尚未敲定**（风险：中，流程风险）。"NativeWind / Tamagui" 写成二选一，说明这个决策在 v4.0 这个号称定稿的版本里还没拍板。这两者范式差异很大（前者是 Tailwind 工具类、后者是带性能优化的组件系统），晚定会直接影响开发节奏，建议在进入实现前先确定。

- **缺少测试策略和可观测性的描述**（风险：中）。一个涉及本地数据库、相机、AI 降级、多层数据同步的应用，状态组合复杂，但全文没有提到单元/集成测试策略，也没有提到崩溃上报（如 Sentry）。考虑到这是店主依赖的生产工具，建议至少补充：核心降级逻辑（AI↔搜索、N1↔本地↔WebDAV）的测试覆盖要求，以及生产环境崩溃监控。

- **冷启动 < 2s 的目标缺乏实现路径**（风险：低中）。13 节给了指标但没说怎么达成，1000+ 商品的本地 hydration、相机权限检查等都可能拖慢启动，建议明确"先渲染骨架屏，商品列表异步加载"这类渐进式启动策略。

## 三、三层数据策略缺陷

- **全量拉取/推送 + 无版本号机制，是这份文档里最核心的数据完整性风险**（风险：高）。9.2 的 N1 API 只有 `sync`（全量拉取）和 `push`（推送变更）两个端点，没有看到任何 updatedAt/版本号/ETag 之类的并发控制字段。这意味着如果两端（比如本地离线编辑了一段时间，N1 端同时也被改了）发生冲突，大概率是"后写覆盖先写"（last-write-wins），且覆盖是静默的、用户无感知。建议至少给 Product 加上服务端可比对的版本字段，sync/push 时做基于时间戳的冲突检测，冲突时弹出"以本地为准/以服务器为准"的选择，而不是默默吞掉。

- **离线变更队列（outbox）未定义，重连顺序是个陷阱**（风险：高）。设备离线时本地编辑商品，重新联网后是先 push 本地队列再 sync，还是先 sync 覆盖本地再去判断要不要 push？这个顺序问题没有写明，如果先 sync 覆盖，本地未推送的变更会被直接冲掉。建议明确定义"重连恢复"的标准时序：先 push 本地未同步变更 → 服务端合并/冲突检测 → 再做全量 sync 拉取最终结果。

- **关于"N1 在线时隐藏 WebDAV 配置"这个问题，你的直觉是对的**（风险：高）。隐藏配置入口意味着用户在 N1 健康运行的大部分时间里根本没有机会、也没有被提示去配置 WebDAV 账号密码。等到 N1 真的意外掉线（服务器故障、断电、网络中断）这个最需要兜底的时刻，WebDAV 反而是从零开始配置——这违背了"灾备"应该提前准备好的基本原则。建议把 WebDAV 配置改为"始终可设置"，只是把"日常使用走 N1 还是 WebDAV"这一层选择逻辑做成自动判断，配置本身不应该被隐藏，只隐藏"当前实际生效路径"的展示。

- 不过这里需要澄清一点容易被误读的地方：**N1 掉线并不等于 App 完全瘫痪**（说明，非风险项）。本地 SQLite 本身就是离线优先的常驻副本（9.1 写"始终运行；离线可用"），所以查价、加购、结账这条主流程在 N1 掉线时仍然能正常工作，真正受影响的是"多设备之间互相同步"和"换新设备/异地备份恢复"这两件事——而这恰恰是 WebDAV 该补位、却因为隐藏配置而补不上的地方。

- **AI Key 完全托管在 N1、没有本地加密缓存**（风险：中）。如果店内网络能直连公网 AI 服务，但只是 N1 这台本地服务器临时挂了，按当前设计 App 仍然会整体降级到搜索模式，即使理论上可以绕过 N1 直接用 AI。这是否可接受取决于产品取舍（AI 本来就是可选增强），但建议至少缓存"最近一次从 N1 拿到的有效 AI 配置"（加密存储），N1 短暂故障时可以临时直连，不必每次都被迫降级。

- **软删除 + 重复检测逻辑在多设备并发下的边界情况未定义**（风险：中）。设备 A 软删除某商品的同时，设备 B（或店主在 N1 后台）新增了同名同规格商品触发"5.4 恢复条目"逻辑，两者谁赢没有规则，建议在冲突检测机制补齐后一并覆盖这类场景。

- **完全没有冲突展示 UI**（风险：中）。即使补了版本号检测，目前的设计里也没有任何"冲突发生时如何呈现给用户"的界面构想，建议至少设计一个轻量的冲突列表（类似 11.4 的重复检测 A/B 卡片样式可以复用）。

## 四、管理模式设计评估

- **连击标题 5 次进入管理模式**（风险：低中）。作为防止顾客/普通店员误触的隐藏入口是合理的，但对店主本人而言，每次都要连点 5 次略显繁琐，且对"临时帮忙看店的家人"完全没有可发现性（如果店主希望授权给他们）。建议保留连点手势作为快速入口，同时在侧滑抽屉底部加一个不显眼但可见的"切换至管理模式"选项——两者都仍然需要 PIN 验证，安全性不打折，只是降低"怎么进去"这一步的认知门槛。

- **PIN 无时效 + 仅靠 App 重启退出，缺乏闲置超时，是个真实的安全隐患**（风险：高）。手机/平板在便利店柜台间传递是常态，店主进入管理模式后短暂离开柜台，在 App 没有被真正"重启"（安卓后台进程往往长期驻留，用户很少主动杀进程）的情况下，任何接触到设备的人都能在管理模式下新增/编辑/删除商品，甚至改 N1 地址和 AI 配置。建议加一个闲置超时自动退出（比如 5-10 分钟无操作），以及 App 进入后台或锁屏时自动退出管理模式，而不是仅依赖"重启"这个粒度过粗的边界。

- **"清空商品库"没有任何二次确认的描述**（风险：高）。10.1 把"清空商品库"列为管理模式可用操作之一，但全文没提到确认弹窗、二次输入校验或其他防误触机制，对比 11.3 批量管理至少还有 CheckBox 逐项勾选，"清空"这种一键销毁全部数据的操作反而更危险却描述更少。建议强制二次确认弹窗，明确文案说明"将软删除全部 XX 件商品，可从 N1/WebDAV 恢复"，必要时要求重新输入 PIN 做二次校验。值得一提的是，由于 5.4 规定禁止物理删除，"清空"本质上也只是批量软删除，数据理论上可恢复，这点应该在确认文案里讲清楚以降低用户的恐慌，但二次确认本身仍然不可省略。

- **PIN 遗忘没有任何恢复路径**（风险：中）。14 节写"PIN 哈希存储，不可找回"，意味着店主一旦忘记 PIN，永远无法再进管理模式新增/编辑商品，除非清空 App 数据重新开始。建议至少设计一条服务端侧的恢复路径——比如通过 N1 后台生成一次性恢复码来重置 PIN，而不是让用户彻底锁死。

## 五、架构扩展性

- **接入微信/支付宝支付，会与当前"结账无记录"的核心设计正面冲突**（风险：高）。真正的支付集成至少需要：(1) 一张全新的 Order/Transaction 表，记录订单号、商品明细快照、应收/实收/找零、支付方式、支付状态、操作时间；(2) 支付状态机（待支付/支付中/已支付/已退款/支付超时）；(3) 与微信支付/支付宝官方 SDK 或聚合支付平台的对接，涉及商户资质、异步回调验证、订单轮询、退款流程，这些都是全新的子系统，不是在现有"结账按钮"上加一个支付选项就能搞定的。更关键的是，现在"确认后清空购物车，不生成任何记录"这个设计本身就要被推翻重做——它和支付场景下"支付成功但本地清空失败/支付失败但本地误清空"这类异常处理是根本冲突的。建议即使 v4 不实现支付，也应该在数据模型层预留 Order 实体的占位结构，避免未来推倒重做整个结账流程。

- **多台设备共享 N1 数据，当前 API 设计撑不住**（风险：高）。9.2 列出的四个端点没有设备身份标识（device_id），无法区分变更来源；没有版本/时间戳并发控制（维度三已详述）；所谓"本地变更实时推送"在只有 REST 端点、没有 WebSocket/SSE 之类双向通道的情况下，实际上更可能是"A 推送变更后，B 并不会被动收到通知，必须自己轮询 sync 才能拿到最新数据"，也就是说多设备间的"实时性"目前是名不副实的。如果多设备协作是近期路线图，建议优先补齐：设备标识、增量同步（而非全量 sync）、基于时间戳/版本号的冲突检测，再考虑是否需要升级到长轮询或 WebSocket 实现真正的主动推送；如果短期仍是单店单设备，这条可以作为已知技术债先记录下来，不必现在解决。

---

如果只能优先处理三件事，我会选：三层数据的版本号/冲突检测机制、管理模式的闲置超时、清空商品库的二次确认——这三个都是"现在改成本低，上线后改成本高且有真实数据/安全损失风险"的类型。
