下面是基于《PStore V4 规格书》的系统性评审结果（）。

---

# 1. 功能边界遗漏

整体流程是“查价优先 + 加购 + 结账”，但在真实便利店操作链路里，仍有几个关键断点没有被覆盖或被弱化。

首先是“查价之外的高频动作缺失”。规格书只强调商品 CRUD 和查价，但便利店实际还存在“临时交易处理”场景，比如临时抹零、赊账记录（小店常见）、手工输入价格商品（无条码临时商品）、套餐拆分（买一送一/组合价）、以及收银异常撤销（刚加购误操作撤回但不影响库存）。这些在当前模型里没有明确数据结构或操作入口。

其次是主流程断点集中在“识别 → 加购 → 结账”之间的状态连续性。当前设计里加购是直接写入购物车，但没有“草稿订单”或“会话级状态”，导致如果 App 崩溃或切后台，购物车恢复依赖不明确。另外查价结果与加购动作是耦合的，但没有中间确认层，AI 或扫码误识别会直接进入购物车，缺少“可回滚链路”。

错误状态处理目前偏弱。网络断开、AI 超时、Vision Camera 无权限、SQLite 损坏、FTS 索引异常这些都没有统一状态机描述。尤其 SQLite FTS5 在损坏或重建时，搜索能力会直接退化，但规格书没有定义 fallback（例如全表 scan 或简化索引）。

扫码无匹配场景有处理，但只覆盖 UI 提示和“可新增商品”，缺少“临时条码挂单”机制。如果店员扫描的是不存在但必须立刻结账的商品，这条链是断的。

---

# 2. 技术风险点

React Native 0.76 + Expo SDK 52 组合是可行的，但在这个项目里属于“边界偏激进”的组合。

首先 Expo SDK 52 逐步强化 native module 管理，但 vision-camera 属于典型的“需要 prebuild + config plugin + 自定义 native code”的模块，在 Expo managed workflow 下很容易进入 EAS prebuild 复杂度。后期如果引入扫码性能优化或自定义 frame processor，会强依赖裸构建，Expo 抽象会变弱。

React Native 0.76 本身稳定，但新架构（Fabric/TurboModules）在 expo-sqlite + vision-camera + Zustand 混用时，会出现“桥接边界不一致”的问题，尤其是 SQLite 高频写入（购物车 + 搜索索引）可能触发 JS thread 阻塞。

expo-sqlite + FTS5 在 1000+ 商品规模下是“能用但不稳”的区间。FTS5 在移动端 SQLite 里性能主要取决于：

* 是否开启 WAL
* 是否做增量 index rebuild
* 查询是否走 prefix match

在 1000~5000 商品时，纯 name/alias/pinyin FTS 查询一般在 5~30ms，但问题不在查询，而在写入同步更新 FTS index 时的卡顿。购物车和商品管理如果高频写入，会出现 UI 卡顿抖动。

vision-camera 在低端安卓机（尤其 MTK 低端 SoC）存在两个典型问题：

* frame processor 丢帧（扫码延迟波动明显）
* autofocus + exposure hunting 导致识别不稳定

如果没有做 frame skipping + debounce + native barcode scanning（MLKit / ZXing native），纯 JS 层扫码稳定性是有风险的。

---

# 3. 三层数据策略缺陷

当前 N1 → 本地 → WebDAV 的设计在“可用性”上是成立的，但一致性模型是弱定义的。

最大问题是：没有明确“单写源（single writer）”还是“多写源并发模型”。

现在描述更像：

* N1 是主
* 本地是副
* WebDAV 是兜底

但没有定义：

* 本地修改是否允许在 N1 在线时发生
* 冲突优先级（N1 vs 本地 vs WebDAV）
* 是否存在版本号/向量时钟

结果是：一旦出现“离线修改 + 在线同步”，冲突会变成“最后写入覆盖”，而不是可控合并。

第二个问题是离线写入后上线的合并策略完全缺失。比如：

* 离线修改商品价格
* 同时 N1 端也修改同一商品
  上线后没有 diff 层，无法判断字段级冲突，只能整条覆盖。

第三个问题是 N1 在线时隐藏 WebDAV 配置，这在 UX 上是合理的，但从可靠性角度会带来误解：用户会认为 WebDAV 是“备用兜底”，但实际上在 N1 在线时完全不可配置，等于被架构屏蔽。如果 N1 出现部分故障（API 可达但数据错误），系统没有真正的第三兜底路径。

---

# 4. 管理模式设计评估

连击标题 5 次 + PIN 是一个典型“隐藏入口 + 权限解锁”模式，但在真实收银场景里存在几个问题。

首先是交互发现性极低。连击标题属于不可学习交互，培训成本高，而且误触概率也不低（尤其低端安卓触控不稳定时）。更关键的是，这种入口无法通过系统层行为提示（例如长期未操作提示进入管理模式）。

替代方案一般会是：

* 长按顶栏 + PIN
* 或侧滑抽屉长按区域 + PIN
* 或扫码管理员卡

当前方案偏“隐蔽安全”，但牺牲了可维护性。

PIN 无时效 + 重启退出的策略是合理的折中，但存在一个问题：如果设备长期运行（便利店设备通常 7x24），管理模式可能被长期保持，等同“弱会话锁定”。这会让 PIN 机制变成一次性门禁，而不是持续权限控制。

更关键的是“清空商品库”在管理模式中存在，但规格书没有描述二次确认机制（如输入 DELETE 或长按确认）。在收银系统里，这属于高破坏性操作，误触成本极高，目前是设计空洞。

---

# 5. 架构扩展性

如果未来接入支付（微信/支付宝），当前架构需要做一次结构性补丁。

主要缺失点是“订单模型”。

现在系统只有：

* 商品
* 购物车（临时）

但支付系统必须引入：

* Order（订单实体）
* Payment（支付状态机）
* Transaction log（不可变流水）

否则“结账即清空购物车”的设计会直接冲突支付链路，因为支付失败/部分支付/退款无法回溯。

另外，支付引入后必须解决：

* 金额锁定（price snapshot）
* 库存扣减时机（支付前还是支付后）
* 异常恢复（支付成功但本地失败）

当前架构没有这些抽象层。

多设备共享 N1 数据同步策略目前是“中心同步模型”，但没有冲突解决机制，所以扩展到多设备时会出现典型问题：

* A 设备改价
* B 设备改库存
* 同步后覆盖

当前设计更像“单写多读”，如果未来变成多终端收银，需要升级为：

* 事件日志同步（append-only）
  或
* CRDT / 版本向量控制（轻量级即可）

否则一致性不可控。

---

# 总体结论（非功能性）

这个 V4 规格书在“单机便利店工具”层面是完整的，但在三个方向存在结构性缺口：

1. 状态机不完整（购物车/订单/错误状态）
2. 同步模型弱一致（N1/本地/WebDAV缺冲突机制）
3. 扩展支付能力缺核心领域模型（Order/Payment）

如果保持当前范围（查价 + 加购 + 简单结账），可以落地；如果要继续扩展成“收银系统”，当前设计需要先补状态机与数据一致性层，否则后期会出现结构性返工。
