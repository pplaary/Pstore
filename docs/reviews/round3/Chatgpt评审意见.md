基于 v4.2（）重新评审，这一版已经明显进入“收敛完成态”，核心目标不再是补功能，而是压复杂度与限定边界。因此评审重点会从“缺什么”转向“哪些地方已经过度设计或存在隐性不一致”。

---

# 1. 功能边界遗漏

**结论：功能层基本闭合，主要问题变成“边界内一致性”而非缺功能（低风险）**

这一版已经明确：

* 非 POS
* 不支付
* 不订单
* 不库存
* 单设备单人
* <1000 商品为主

这使得绝大多数传统收银/进销存问题不再适用。

但仍有三个边界内问题：

### 1.1 “查价 → 加购”链路仍缺“统一决策层”

现在三条入口：

* AI
* 扫码
* 搜索

但它们最终都进入“商品卡片 → 加购”UI层。

缺失的是一个“统一结果归一层”，导致：

* AI 输出结构
* 扫码输出结构
* 搜索输出结构

语义不完全一致（例如 AI 有 confidence，但扫码没有）

长期会导致 UI 判断逻辑分散。

风险等级：中

---

### 1.2 PendingItem 仍是“孤立数据结构”

PendingItem 现在是：

* 扫码失败 → 存
* 管理模式再处理

问题在于：

* 它没有生命周期状态（未认领 / 已认领 / 已忽略）
* 没有自动合并策略

在 <1000 商品场景下会变成“轻量垃圾桶”。

风险等级：低（但会累积体验问题）

---

### 1.3 “模拟结账”语义仍有轻微歧义

虽然已声明“不做交易”，但：

* 购物车
* 清空
* 合计
* 查看合计

在 UI 语义上仍接近 POS。

风险不在技术，而在“认知误导”，后期可能会导致扩展方向被误读。

风险等级：低

---

# 2. 技术风险点

**结论：技术栈基本稳定，风险从“框架问题”转为“实现复杂度问题”（低~中风险）**

相比 v4.1，v4.2 实际上没有再增加重技术负担，反而做了两件关键优化：

* iOS 明确不在首期范围（降低复杂度）
* MLKit 固定（减少 vision-camera 不确定性）

但仍存在三个点：

---

### 2.1 SQLite + FTS + PriceHistory 写路径复杂度仍存在

虽然规模 <1000，但写路径仍是：

* product update
* searchText update
* FTS index update
* PriceHistory insert（可能触发）

问题不是性能，而是：

> 写逻辑分散在多个模块时容易产生“隐式不一致”

风险等级：中

---

### 2.2 MLKit + Expo 仍然是“工程耦合点”

虽然限定 Android，但：

* Expo prebuild
* vision-camera plugin
* MLKit native binding

仍然是唯一“可能卡住发布”的点。

风险等级：中（但可控）

---

### 2.3 NativeWind 引入后 UI 状态分层风险

NativeWind 本身没问题，但在 RN + Zustand + Navigation 组合里：

* UI 状态来源分散
* 样式 + 状态 + 业务混合风险上升

风险等级：低

---

# 3. 数据策略缺陷

**结论：一致性模型已经“工程可用”，但仍是弱一致（中风险下降为低~中）**

v4.2 做了一个关键收敛：

* 明确 device_id（未来扩展）
* 明确单设备场景
* 明确 N1 权威源
* 明确 updatedAt 冲突策略
* 明确恢复路径

这意味着：

👉 已经从“分布式问题”降级为“单写同步问题”

---

### 3.1 冲突策略仍是 last-write-wins

仍然存在结构性限制：

* 字段级冲突不存在
* 多字段并行修改无法合并

但在当前规模下，这是合理的工程折中。

风险等级：低（已接受）

---

### 3.2 WebDAV 已彻底降级为“备份系统”

这是正确方向：

* 不参与实时同步
* 不参与一致性

但缺少一个小问题：

* 没有“备份版本索引”

恢复只能靠最近文件，而不是结构化历史。

风险等级：低

---

### 3.3 N1 单点依赖仍然存在

虽然允许离线，但：

* AI 配置
* 商品权威同步

仍依赖 N1。

如果 N1 挂：
系统退化为“纯本地模式 + 手动恢复”。

这是设计接受的 tradeoff，但仍是系统唯一外部依赖点。

风险等级：中（架构性）

---

# 4. 管理模式设计评估

**结论：这一版已经接近“合理权限系统”，而不是 UI trick（低风险）**

相比 v4.1，这一版最关键改进：

### ✔ 清空商品库 → 强制输入确认

这是非常关键的安全补丁。

---

但仍有两个结构性点：

### 4.1 管理入口“双路径”是合理的，但语义重复

现在：

* 连击标题
* 抽屉按钮

两套入口本质做同一件事。

问题不是功能，而是：

* 权限入口语义分裂

风险等级：低

---

### 4.2 PIN 仍然是“解锁态”，不是“操作级权限”

虽然加了清空确认，但仍存在：

* 解锁一次 = 全功能开放

未来如果扩展敏感操作（例如数据恢复），会再次遇到同样问题。

但在当前范围内可以接受。

风险等级：低

---

# 5. 架构扩展性

**结论：这是这一版最稳定的部分，已经明确收敛到“轻工具系统”（低风险）**

v4.2 做了一个很重要的事情：

> 明确禁止扩展到：

* 多设备协作
* 收银
* 库存
* 对账

这实际上是“冻结了系统形态”。

---

### 5.1 当前架构的真实定位已经固定

不是：

* POS
* 进销存
* 零售系统

而是：

> 单设备商品查价 + 合计工具

这个定位非常清晰。

---

### 5.2 扩展支付已经被彻底排除

因此：

* 不需要 Order 模型
* 不需要 Transaction
* 不需要库存链路

这是一个结构性优势（减少 60% 复杂度）。

---

### 5.3 多设备扩展被延后是正确决策

因为当前系统：

* 没有 event log
* 没有 CRDT
* 没有操作序列

强行多设备会直接重构。

---

# 总体结论（v4.2）

这一版已经进入一个很明确的状态：

> 工程收敛完成版（Feature Stable / Architecture Stable）

它的变化不是“继续增强”，而是：

* 限定场景
* 限定规模
* 限定复杂度
* 限定扩展方向

---

## 主要风险重新排序

| ---------------- | -- |
| SQLite 写路径一致性    | 中  |
| MLKit/Expo 集成    | 中  |
| N1 单点依赖          | 中  |
| PendingItem 生命周期 | 低  |
| UI/权限设计          | 低  |
| 同步模型             | 低  |

---

## 一句话结论

v4.2 已经不是一个“需要补功能的系统”，而是一个“可以直接施工的受控系统”。剩下的问题不在设计层，而在实现阶段的边界守住能力。
