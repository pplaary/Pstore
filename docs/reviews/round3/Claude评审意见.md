# PStore V4.2 规格书复审（第三轮）

先说结论：这轮提交质量很高，上一轮标记的两个高风险遗留项里，**清空商品库二次确认已经完整闭环**，但**管理模式闲置超时这一条，连续三轮都没有被处理**，需要在这轮明确指出来，因为它已经不太可能是巧合性的遗漏了。

## 已确认解决的项目（不再展开分析，逐条确认）

12.6「清空商品库」补得很到位：全屏二次确认 + 文案说明影响范围（"将软删除全部 N 件商品"）+ 要求手动输入"确认删除"四个字 + 明确告知可从 N1/WebDAV 恢复。用"打字确认"代替我原来建议的"重新输入 PIN"，效果是等价的（都是有意识的二次动作，能有效拦住手滑），而且更符合移动端交互习惯，这个选择比我的建议更好。

PendingItem 去重（5.3 barcode UNIQUE + "重复扫描只更新 scannedAt"）、searchText 模糊匹配优先展示连续字命中（6.2）、MLKit 平台范围声明（二、新增"当前目标平台：Android，iOS 需额外适配...不在首批交付范围"）、十七节里给 device_id 留的路标——这四项都按上一轮的建议落地了，方案具体，不需要再挑。

## 唯一仍未处理的高风险项：管理模式闲置超时

这是第一轮（v4.0 评审）就标记为"风险：高"的问题，v4.1 没处理，这次 v4.2 依然没有。11.2 的退出方式还是只有"再次连点标题""点抽屉退出按钮""App 重启"三种，没有任何自动超时或切后台/锁屏自动退出的机制。

需要强调一下为什么这条不在文档开头新加的"适用范围"排除清单里：那份清单排除的是"连锁门店、多人协作、库存管理、收银对账"这类**业务复杂度**层面的场景，但"单店单人单设备"并不等于"手机永远在店主手里"。便利店柜台手机被顾客借用、被家人帮忙照看、放在台面上去后厨拿货，这些都是这个场景里的真实日常，不属于被排除的范畴。店主一旦连点标题进了管理模式，只要 App 进程没被系统杀掉（安卓后台进程驻留是常态，用户很少主动划掉），这段时间内任何接触到设备的人都能改商品、改 N1 地址、改 AI Key，乃至触发刚刚做好二次确认的"清空商品库"。

具体建议很轻量，不需要大改架构：监听 AppState，切到后台或锁屏时立即把管理模式状态置回普通模式；再加一个比如 5-10 分钟无操作的前台闲置计时器兜底。这两个机制都是几行状态管理代码的量级，建议直接补进 11.2，作为这轮唯一需要回去改的条目。

## 两处值得顺手补充的小细节（风险：低，不影响进入开发）

12.5 新增的散装商品快捷入口是个很贴合便利店真实场景的补充（塑料袋、热餐、散装零食确实没条码），但有两处可以在规格里说得更明确一些。一是 5.1 的 barcode 字段写的是"TEXT，唯一"，散装商品大概率没有条码，需要明确这个字段允许 NULL（SQLite 的 UNIQUE 约束本身允许多个 NULL 共存，不冲突，但容易被默认按 NOT NULL 实现，建议在数据模型里点一句）。二是 12.5 写"点击直接加购，无需扫描或打字搜索"——这和 4.2 定义的标准流程（AI/扫码结果先展示卡片，用户点 [加购] 才真正入车）不一样，散装标签是用户主动点击、意图明确，跳过确认卡片是合理的，但建议在规格里补一句说明"这是有意为之的快捷路径，区别于 AI/扫码的自动识别结果"，避免开发时被当成遗漏了确认步骤。

## 残留但优先级低的技术债（前两轮已提过，这里不重复展开）

新架构（Fabric/TurboModules）兼容性验证、测试与崩溃监控策略，这两条仍然没有进规格书，但这类属于"开发启动前的工程清单"而非"产品规格缺陷"，不需要为了它们再卡一轮评审，建议团队在写代码前单独过一遍，不必体现在这份文档里。

如果这轮只改一件事，就是把管理模式的闲置超时补上——这是目前唯一一个跨越三轮评审都没有被处理、且一旦真出问题就是数据安全事故级别的缺口，其余的都已经收得很干净，可以进入开发阶段。
